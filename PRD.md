# PRD — Face-to-Web Discovery & Blockchain Verification

**Document status:** v1.0 — Project foundation  
**Created:** 2026-09-01  
**Project type:** Hackathon / engineering demonstration  
**Primary goal:** Build a genuine end-to-end pipeline that accepts a face image, performs a real web/social-media discovery operation for matching public content, fingerprints the discovered content, records the fingerprint on a blockchain, and re-verifies the content against the on-chain record.

---

## 1. Executive Summary

This project demonstrates the following pipeline:

```text
Face Image
   ↓
Face Detection + Encoding
   ↓
Genuine Web / Public-Social Search
   ↓
Candidate Discovery
   ↓
Face/Content Match Evaluation
   ↓
Retrieve Discovered Public Content
   ↓
Canonicalize Evidence
   ↓
SHA-256 Fingerprint
   ↓
Blockchain Registration
   ↓
Independent Re-fetch / Re-hash
   ↓
On-chain Verification
   ↓
VERIFIED / TAMPERED / NOT_FOUND
```

The project must not fake any stage. Search results must be obtained at runtime from a real search/reverse-search service or other legitimate public-web discovery mechanism. Blockchain records must be generated by an actual transaction on the selected network or a clearly documented local blockchain.

The blockchain is an **integrity/provenance layer**. It does not prove that a person owns an account, that an image is authentic in the real-world sense, or that a face belongs to a particular legal identity.

---

## 2. Problem Statement

Given an input photograph containing a face, the system should:

1. Detect the face.
2. Generate a machine-readable face representation.
3. Perform a genuine search for matching public web/social content.
4. Present discovered candidates and evidence.
5. Select or confirm a matching candidate using explicit matching logic.
6. Create a deterministic fingerprint of the discovered evidence.
7. Write the fingerprint and minimal provenance metadata to a blockchain.
8. Recalculate the fingerprint later and compare it with the on-chain record.
9. Clearly report whether the evidence still matches the recorded state.

The system should remain useful when the input subject has only a small public web footprint. Search failure must be represented honestly rather than replaced with hardcoded demo data.

## 4. Core Requirements

### R1 — Face Detection and Encoding

Input:
- JPG/JPEG/PNG/WebP image
- One or more visible faces

Required behavior:
- Validate file type and size.
- Decode image safely.
- Detect faces.
- Select a face deterministically if multiple faces are present, or require explicit selection.
- Generate an embedding using the chosen face-recognition library.
- Record model/library version in internal run metadata.

Minimum response:

```json
{
  "detected": true,
  "face_count": 1,
  "selected_face": 0,
  "embedding_generated": true
}
```

The embedding must not be written to a public blockchain.

### R2 — Genuine Web/Public-Social Discovery

The system must execute a real search at runtime.

Acceptable approaches include:
- A legitimate reverse-image/face-search API whose terms permit the intended use.
- A public search API combined with permitted image/content retrieval.
- Another documented public-web discovery mechanism.

The result must not be:
- Hardcoded.
- Preselected in source code.
- Fabricated when the search returns nothing.

The system must preserve:
- Search provider.
- Search/request ID if supplied.
- Search start/end timestamps.
- Number of candidates returned.
- Candidate URLs.
- Match/confidence information when supplied.
- Any provider limitations relevant to interpretation.

### R3 — Matching

Candidate ranking must be deterministic and explainable.

Possible signals:
- Face similarity score.
- Image similarity score.
- Exact/near-exact image fingerprint.
- Source URL validity.
- Provider confidence.

Never present an arbitrary result as a confirmed match merely because it is the first search result.

Use explicit statuses:

```text
MATCH_CONFIRMED
MATCH_POSSIBLE
NO_MATCH
SEARCH_FAILED
RETRIEVAL_FAILED
```

### R4 — Evidence Capture

For the selected public result, capture only information necessary for provenance:

```text
source_url
canonical_url (if safely determined)
page title
caption/text where legally and technically permissible
retrieved_at
source/provider
image bytes if permitted/needed
content type
HTTP metadata if available
```

Do not store unnecessary personal information.

### R5 — Deterministic Fingerprinting

The system must create a canonical evidence object.

Example:

```json
{
  "schema_version": "1.0",
  "source_url": "https://example.invalid/post",
  "title": "Example",
  "text": "Example text",
  "image_sha256": "…",
  "retrieved_at": "2026-09-01T18:00:00Z"
}
```

Important:
- `retrieved_at` should generally NOT be included in the integrity hash if the goal is to verify content equality across later retrievals.
- Hash the stable evidence representation.
- Sort JSON keys.
- Use UTF-8.
- Define whitespace normalization.
- Define newline normalization.
- Define Unicode normalization.
- Define how missing/null fields are represented.
- Use SHA-256 unless a documented reason exists to use another cryptographic hash.

### R6 — Blockchain Registration

Store a compact record on-chain.

Recommended fields:

```text
bytes32 evidenceHash
uint256 recordedAt
address submitter
string schemaVersion
```

Do not store:
- Raw face images
- Face embeddings
- Full social-media content
- Private personal information

The application must retain the blockchain:
- network
- chain ID
- contract address
- transaction hash
- block number
- evidence hash

### R7 — Verification

Verification must perform a fresh hash calculation.

```text
Current evidence
       ↓
Canonicalization
       ↓
SHA-256
       ↓
Current hash
       ↓
Read blockchain
       ↓
On-chain hash
       ↓
Exact comparison
```

Return:

```json
{
  "verified": true,
  "tampered": false,
  "local_hash": "...",
  "on_chain_hash": "...",
  "transaction_hash": "..."
}
```

If the hashes differ:

```json
{
  "verified": false,
  "tampered": true,
  "reason": "HASH_MISMATCH"
}
```

## 5. User Stories

### US-01 — Upload
As a tester, I can upload a face image and see whether a face was detected.

### US-02 — Search
As a tester, I can initiate a genuine search and see runtime-discovered candidates.

### US-03 — Inspect
As a tester, I can inspect the selected candidate and understand why it was selected.

### US-04 — Register
As a tester, I can register the evidence fingerprint on the blockchain.

### US-05 — Verify
As a tester, I can re-run verification and see whether the content still matches.

### US-06 — Demonstrate tampering
As a tester, I can modify evidence locally and see verification fail.

### US-07 — Recover from failure
As a tester, I receive a useful error instead of a fake success when search, retrieval, or blockchain operations fail.

## 6. Functional Requirements

### Input validation
- Maximum upload size must be configurable.
- Reject unsupported formats.
- Reject corrupt images.
- Handle EXIF orientation.
- Avoid processing excessively large images without resizing.
- Never trust client-provided MIME type alone.

### Search
- Search operation receives a unique `run_id`.
- Search provider calls must have timeout/retry policies.
- Retries must use exponential backoff and bounded attempts.
- Rate limits must be respected.
- Search provider credentials must remain server-side.

### Candidate processing
- Candidate URLs must be normalized without accidentally changing semantics.
- Do not automatically follow dangerous schemes such as `javascript:`.
- Use HTTP(S) only.
- Apply request timeouts and response-size limits.

### Blockchain
- Transactions must be idempotent where practical.
- Duplicate evidence hashes should not create unnecessary duplicate registrations.
- Transaction status must be confirmed before reporting success.
- Chain ID must be verified.
- RPC failures must be surfaced.

---

## 7. Non-Functional Requirements

### Reliability
- No hardcoded success path.
- Every stage reports explicit status.
- Partial failures are retained in the run record.

### Security
- API keys only in environment variables/secrets.
- No private keys in Git.
- No blockchain private key in frontend code.
- Validate all uploaded files.
- Limit request sizes.
- Sanitize logs.

### Privacy
- Face embeddings are sensitive biometric representations.
- Minimize retention.
- Do not place biometric templates on-chain.
- Provide deletion/cleanup for temporary files.
- Do not search private content or bypass access controls.

### Reproducibility
Every pipeline run should have:
- run ID
- software version
- model version
- search provider
- blockchain network
- contract address
- timestamps
- stage statuses

## 8. Success Criteria

The project is successful only if a live demonstration can show:

1. A real input face is accepted.
2. Face detection/encoding actually runs.
3. A real search is triggered.
4. At least one runtime-discovered public result is returned when the test subject has indexed public content.
5. The discovered evidence is fingerprinted.
6. A blockchain transaction is created.
7. The transaction is confirmed.
8. The same evidence is re-hashed.
9. The local hash equals the on-chain hash.
10. A modified evidence object produces a different hash and fails verification.

Search failure must also be demonstrable and must not be treated as an application bug if the external provider has no matching result.

## 9. Demo Acceptance Test

### Test A — Happy path
Input: consenting test user's public photo.

Expected:
- Face detected.
- Search executes.
- Candidate returned.
- Evidence selected.
- Hash generated.
- Blockchain registration confirmed.
- Verification = TRUE.

### Test B — Tampering
Modify one stable evidence field.

Expected:
- New hash differs.
- On-chain hash unchanged.
- Verification = FALSE.

### Test C — No public match
Use a face with no indexed public content.

Expected:
- Search executes.
- No result is returned.
- System reports `NO_MATCH`.
- No fake blockchain registration is created.

### Test D — Blockchain unavailable
Temporarily disable RPC.

Expected:
- Search still reports correctly.
- Blockchain stage reports failure.
- UI does not claim verification.
